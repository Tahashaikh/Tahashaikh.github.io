Playwright waitForTimeout: The Flake You Can Delete

A fixed sleep guesses. In our lab, a 250 ms wait passed 6 of 20 runs. Here is the replacement and when a fixed wait is still valid.

By Muhammad Taha Tariq , Software Automation Engineer & Editor Published October 25, 2026 Updated October 25, 2026 6 min read

A fixed wait is a guess about time. A web-first assertion is a check on state. In 20 lab runs, the fixed 250 ms wait passed 6 times. The state-based version passed every fixed run.

QA engineers removing fixed sleeps from a Playwright suite
Price / effort
Free. Playwright is open source.

October 2026

What we checked

  • 20 runs with a 250 ms fixed wait
  • 20 fixed runs with a web-first assertion
  • Playwright 1.64.1 and Chromium 1248

What we did not check

  • Your application and CI runner
  • Mobile browsers
  • Delays caused by a third-party service you do not control

In Playwright, waitForTimeout is a guess about time. The test says “250 ms is enough”. The application says “sometimes it is, sometimes it is not”. When the two disagree, the test fails and the code is fine.

In our lab, a 250 ms wait passed 6 of 20 runs. The page showed “Saved” after a random delay between 100 and 600 ms. The test read the status once, at 250 ms. When the save took longer, the test read “idle” and failed.

The fix was one line. The fixed version passed every run.

What the lab measured

The page had a Save button. A click started a timer. The status changed to “Saved” after a random delay between 100 and 600 ms. The test did this:

await page.getByTestId('save').click();
await page.waitForTimeout(250);
expect(await page.getByTestId('status').textContent()).toBe('Saved');

Result: 6 of 20 runs passed. 14 failed.

The test did not fail because the click was wrong. It did not fail because the locator was wrong. It failed because 250 ms is not a property of the application. It is a property of the test author’s hope.

Why does the check after the sleep still fail?

A sleep does not make the next line wait. It only delays it. The next line runs once.

  • textContent() reads the text at that moment. It does not retry.
  • isVisible() returns a snapshot. It does not retry.
  • A plain expect(value).toBe(...) compares one value. It does not retry.

If the state is not ready when the line runs, the test fails. The sleep moved the start time. It did not create a condition.

This is the subtle part. Many people add a sleep before a retrying assertion and think the sleep is the fix. The retrying assertion is the fix. The sleep only adds time.

The replacement

Use a web-first assertion. It checks the state again until the condition is true or the timeout ends.

await page.getByTestId('save').click();
await expect(page.getByTestId('status')).toHaveText('Saved', { timeout: 2000 });

Result: 20 of 20 fixed runs passed (5 repeats per pattern).

The assertion does not care whether the save takes 100 ms or 600 ms. It cares that the text becomes “Saved” within 2 seconds. That is the real requirement. The old test encoded a guess. The new test encodes a rule.

The same idea works for other states:

await expect(page.getByTestId('loading')).toBeHidden();
await expect(page.getByRole('button', { name: 'Save' })).toBeEnabled();
await expect(page.getByTestId('row')).toHaveCount(3);

Each one retries. Each one fails with a message that names the state. None of them guesses a duration.

The network case

A fixed wait is often used before a network call:

await page.getByTestId('submit').click();
await page.waitForTimeout(1000);
expect(await page.getByTestId('result').textContent()).toBe('done');

This has two problems. The sleep may be too short, and the wait may start after the response. In our lab, calling waitForResponse after the click failed 14 of 20 runs. The response can arrive before the wait is set up.

Start the wait before the action:

const [response] = await Promise.all([
  page.waitForResponse('**/api/submit', { timeout: 2000 }),
  page.getByTestId('submit').click(),
]);
expect(response.status()).toBe(200);

If the next line needs a rendered value, assert the value. If it needs a specific response, wait for that response. Do not use a sleep for either job.

When a fixed wait is valid

A fixed wait is valid when the wait is the condition. Three examples:

  1. You are testing a rate limit. The product should reject a second request inside 1 second. The wait is part of the rule.
  2. You are testing a debounce. The product should wait 300 ms after typing. The wait is the behavior under test.
  3. You are debugging. A temporary sleep can help you see a state. Remove it before you commit.

There is a fourth case that looks valid but is not: animation. Do not wait for an animation to finish. Disable animations in the test configuration, or assert the end state.

use: {
  launchOptions: { args: ['--force-prefers-reduced-motion'] },
}

If a third-party service is slow, do not sleep longer. Mock the service, or move that check to a separate integration suite with its own timeout.

How to find fixed waits

Start with a search:

grep -R "waitForTimeout" tests/

If the suite uses eslint-plugin-playwright, enable the no-wait-for-timeout rule. It flags the call at review time, before it becomes a flake. Then replace each hit with the state the next line needs:

  • Waiting for text? toHaveText().
  • Waiting for an element? toBeVisible().
  • Waiting for a count? toHaveCount().
  • Waiting for a response? waitForResponse() before the action.
  • Waiting for a URL? waitForURL().
  • Waiting for a loading state to end? toBeHidden().

If you cannot name the state, the test does not know what it is waiting for. That is the real bug.

A four-step removal plan

Do not rewrite the whole suite in one go. Fix one spec and measure it.

  1. Pick one failing spec. Choose the test that fails most often, not the one that is easiest to edit.
  2. Record the baseline. Run it 20 times with one worker. Write down the pass and fail counts.
  3. Replace the wait. Use the state the next line needs. If you cannot name the state, stop and read the test again.
  4. Run the same 20 times. Compare the counts. If the failure rate does not drop, the wait was not the cause.

Put the before and after counts in the pull request. A reviewer can see the evidence in ten seconds. “It feels more stable” is not evidence.

If the test still fails, do not add a longer sleep. Look at the trace. The cause may be shared state, a locator, or the environment.

Do not raise the global timeout

A common response to a flaky test is to raise the test timeout. That makes the failure slower. It does not make the test more reliable. It can also hide a performance regression: a page that used to load in 2 seconds now takes 12, and the suite still passes.

Keep the global timeout generous enough for slow CI. Keep each assertion timeout tight enough to fail with a useful message. Fix the condition, not the clock.

The short answer

A fixed wait is a guess. A web-first assertion is a check. Replace the guess with the check.

In the lab, the fixed 250 ms wait passed 6 of 20 runs. The state-based version passed 20 of 20 fixed runs. The difference was not a longer timeout. It was a better question: “Is the state ready?” instead of “Has enough time passed?”

Frequently asked questions

Is waitForTimeout always wrong?

No. It is valid when the wait itself is the condition under test, such as a rate limit or a deliberate debounce. It is wrong when it replaces a check on the page state. If you cannot explain why the number is correct, remove it.

Does a longer wait fix a flaky test?

No. It makes the failure slower. A longer wait can also hide a real performance problem. Fix the condition the next line depends on.

What should I use instead?

Use a web-first assertion such as expect(locator).toHaveText(), toBeVisible(), or toHaveCount(). These checks retry until the condition is true or the timeout ends. For a network dependency, start waitForResponse before the action.

How do I find every fixed wait in a large suite?

Search for waitForTimeout. If you use eslint-plugin-playwright, enable the no-wait-for-timeout rule. Then replace each hit with the state the next line needs.
