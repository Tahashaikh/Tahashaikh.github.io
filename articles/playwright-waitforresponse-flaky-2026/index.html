Playwright waitForResponse: Subscribe Before You Click

Calling waitForResponse after the click lets a fast API win the race. In our lab, 14 of 20 runs failed. Here is the Promise.all fix and a precise predicate.

By Muhammad Taha Tariq , Software Automation Engineer & Editor Published October 25, 2026 Updated October 25, 2026 5 min read

This is a Playwright waitForResponse race. The test clicks Submit. The API answers in 5 ms. Then the test starts waiting for the response. It waits for 1 second and fails. The network tab shows the response. The test says it never arrived.

This is a race. page.waitForResponse() starts listening when you call it. It does not look back. If the response arrives before the call, the wait has nothing to catch.

In our lab, the after-click version passed 6 of 20 runs. The other 14 timed out. The fix was to start the wait before the click. The fixed version passed every run.

What the lab measured

The page had a Submit button. A click sent POST /api/submit. The server answered immediately. The test did this:

await page.getByTestId('submit').click();
const response = await page.waitForResponse('**/api/submit', { timeout: 1000 });
expect(response.status()).toBe(200);

Result: 6 of 20 runs passed. 14 failed.

The failure message is a timeout. That is confusing. The request did succeed. The test missed it.

Why does the order matter?

A click is not a single instant. The browser dispatches the event, the handler starts the request, and the click call returns. The response can arrive before the next line runs.

The sequence looks like this:

  1. Click.
  2. Request starts.
  3. Response arrives.
  4. waitForResponse starts listening.
  5. Nothing arrives. Timeout.

On a fast local API, steps 2 and 3 can finish before step 4. On a slower CI runner, the same code may pass. That is why the test is flaky, not broken.

The fix: start the wait first

Create the wait before the action. Then await both.

const [response] = await Promise.all([
  page.waitForResponse('**/api/submit', { timeout: 2000 }),
  page.getByTestId('submit').click(),
]);
expect(response.status()).toBe(200);

Promise.all starts both promises. The wait is listening before the click sends the request. The response cannot slip through.

You can also create the promise first:

const responsePromise = page.waitForResponse('**/api/submit', { timeout: 2000 });
await page.getByTestId('submit').click();
const response = await responsePromise;
expect(response.status()).toBe(200);

Use Promise.all for one action and one response. Use the second form when the action is complex, or when you need to do something between the click and the await.

Fixed result: 20 of 20 fixed runs passed (5 repeats per pattern).

Make the predicate precise

A broad pattern is a second race. **/api/* can match a preflight, a retry, a background refresh, or a different endpoint that happens to share the path.

Use the URL, the method, and the status:

const response = await page.waitForResponse(
  (res) =>
    res.url().endsWith('/api/submit') &&
    res.request().method() === 'POST' &&
    res.status() === 200,
  { timeout: 2000 },
);

This predicate only accepts the response you want. It also fails faster when the server returns 500, because the wait does not accept the error response and the assertion can report it.

When the endpoint is called more than once

Some pages call the same endpoint several times: polling, retries, or a refresh after save. One waitForResponse catches one response. If you need two, start two waits, or collect responses with an event listener.

const responses: Response[] = [];
page.on('response', (res) => {
  if (res.url().endsWith('/api/orders')) responses.push(res);
});

await page.getByTestId('submit').click();
await expect.poll(() => responses.length).toBe(2);

An event listener is useful when the number of calls is part of the behavior. A single waitForResponse is better when you need one specific reply.

If the API includes a request ID, put it in the predicate. That is the cleanest way to separate two calls to the same URL.

A five-point checklist

Before you add a response wait, check these five points:

  1. Order. Is the wait created before the action that sends the request?
  2. Match. Does the predicate include the URL, the method, and the status?
  3. Timeout. Is the wait timeout shorter than the test timeout, so the failure names the wait?
  4. Payload. Do you check the fields the next step depends on?
  5. UI. Do you assert what the user sees, not only what the server returned?

A wait that passes all five is easy to read and hard to flake. A wait that misses one is a future bug report. Use the checklist before you merge, not after a red build.

The timeout point matters. If the test timeout is 30 seconds and the wait timeout is also 30 seconds, the test dies before the wait can explain itself. Set the wait to 2–5 seconds for a local API, or to a number that matches the service level you expect.

A response is not a result

A 200 means the server replied. It does not mean the payload is correct, the UI updated, or the business rule passed.

Check the status first:

expect(response.status()).toBe(200);

Then check the payload fields you depend on:

const body = await response.json();
expect(body).toMatchObject({ ok: true, orderId: expect.any(String) });

Then check the visible result:

await expect(page.getByTestId('result')).toHaveText('done');

Do not stop at the response if the user sees something else. The UI is the part the user experiences.

When to wait for the UI instead

If the next line depends on what the user sees, wait for the UI. The response may arrive before the render.

await page.getByTestId('submit').click();
await expect(page.getByTestId('result')).toHaveText('done');

This is simpler and more robust. It does not care which request produced the text. It cares that the user can see the result.

Use waitForResponse when the test needs to inspect the response itself: status, headers, payload, or a specific call among several. Use a UI assertion when the test only needs the result.

Do not replace it with networkidle

networkidle waits for 500 ms of no network activity. A page with analytics, polling, or a websocket may never reach that state. In our lab, a page that polled every 100 ms made networkidle time out when the poll started inside the quiet window.

If you need a specific response, wait for that response. If you need a rendered value, assert the value. Do not wait for the whole network to be quiet.

The short answer

waitForResponse is a listener, not a time machine. Start it before the action.

In the lab, the after-click version failed 14 of 20 runs. The Promise.all version passed 20 of 20 fixed runs. The difference was one line of order.

Use a precise predicate. Check the status and the fields you need. Then assert what the user sees. A response is evidence. It is not the result.

Frequently asked questions

Why does waitForResponse time out when the request succeeded?

The wait started after the response arrived. waitForResponse only listens from the moment you call it. Start the wait before the action that sends the request.

Should I use Promise.all or create the promise first?

Both work. Promise.all is shorter when one action triggers one response. Create the promise first when the action is complex, or when you need to do something else before awaiting it.

How do I match the right response?

Use a predicate with the URL, the method, and the status. If the endpoint is called more than once, add a request ID or another unique value. A broad glob can match a preflight, a retry, or a background refresh.

Is waiting for the response enough?

No. A response means the server replied. It does not mean the UI updated or the payload is correct. Assert the status, the fields you depend on, and the visible result.
