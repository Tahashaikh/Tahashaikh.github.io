Playwright Flaky Tests: 4 Patterns We Reproduced

We ran four Playwright flaky patterns 20 times each. A fixed 250 ms wait passed 6 of 20. A response wait after the click passed 6 of 20. The fixes passed 20 of 20.

What we did not check

A flaky test passes and fails on the same code. The code did not change. The result changed. That is the whole problem.

Playwright flaky tests usually come from timing, shared state, or a locator that points at a moving target. The framework removes some causes, not all of them.

Most advice stops at “add retries” or “increase the timeout”. Both hide the failure. They do not explain it. So we built a small Playwright lab and reproduced four common patterns. Each pattern ran 20 times. Then we fixed each one and ran the fixed version again.

The lab is small on purpose. It has one page, a few buttons, and four bad habits that appear in real suites. The numbers are not a benchmark of your application. They show what the pattern does when the timing is not on your side.

Why do Playwright tests become flaky?

A test is flaky when the result changes without a code change. The cause is usually outside the assertion: a fixed sleep, a response that arrives before the wait, a page that never goes idle, or an element that is replaced under the click.

The fix starts with the cause, not with a retry setting. The lab below isolates four causes so you can see the mechanism.

We ran each pattern with --repeat-each=20. A pass means the test passed in that run. A fail means it failed without a code change. We did not count a retry as a pass.

The fixed tests ran 5 times each, for 20 fixed runs in total. All 20 passed.

Pattern 1: A fixed 250 ms wait

The page shows “Saved” after a random delay between 100 and 600 ms. The test clicks Save, waits 250 ms, and reads the status once.

await page.getByTestId('save').click();
await page.waitForTimeout(250);
expect(await page.getByTestId('status').textContent()).toBe('Saved');

Result: 6 of 20 runs passed. 14 failed.

When the save takes 300 ms, the test reads “idle” and fails. The application is fine. The test guessed the time.

The fix is not a longer wait. The fix is to wait for the state the user can see.

await page.getByTestId('save').click();
await expect(page.getByTestId('status')).toHaveText('Saved', { timeout: 2000 });

expect(locator).toHaveText() is a web-first assertion. It checks again until the text matches or the timeout ends. It does not guess a duration. It waits for the condition.

This is the most common flake in the lab, and the easiest to remove. Search the suite for waitForTimeout. Replace each one with the state that must be true before the next line.

There is one exception. A fixed wait is valid when the wait is the thing under test, such as a rate limit or a deliberate delay. Then write a comment that says why. Do not use it to make a red test green.

Pattern 2: waitForResponse after the click

The test clicks Submit, then starts waiting for the response.

await page.getByTestId('submit').click();
const response = await page.waitForResponse('**/api/submit', { timeout: 1000 });
expect(response.status()).toBe(200);

Result: 6 of 20 runs passed. 14 failed.

page.waitForResponse() starts listening when you call it. The click returns after the browser dispatches the event. A fast API can answer before the wait is set up. The response arrives, nobody is listening, and the wait times out.

The fix is to start the wait before the action.

const [response] = await Promise.all([
  page.waitForResponse('**/api/submit', { timeout: 2000 }),
  page.getByTestId('submit').click(),
]);
expect(response.status()).toBe(200);

The promise is created before the click. The click and the wait run together. The race is gone.

You can also create the promise first and await it after the click. Promise.all is shorter for one action. The important part is the order, not the syntax.

Pattern 3: networkidle on a page that polls

The page polls /api/analytics every 100 ms. The test waits for networkidle.

await page.goto('/', { waitUntil: 'networkidle', timeout: 2000 });
await expect(page.getByTestId('live')).not.toHaveText('0');

Result: 17 of 20 runs passed. 3 timed out.

The pass or fail depends on when the first poll starts. networkidle waits for 500 ms with no network activity. If the poll starts after that quiet window, the wait resolves. If the poll starts before it, the page never goes quiet. The wait runs until the timeout.

In the first 20-run set, the poll started at a random time between 300 and 900 ms. That is why 3 runs failed and 17 passed. The pattern is not random. It is timing-dependent. When the first poll lands inside the quiet window, the wait cannot settle.

The fix is to wait for the user-visible state, not the network.

await page.goto('/');
await expect(page.getByTestId('live')).not.toHaveText('0', { timeout: 3000 });

If the next step needs a specific response, wait for that response. If it needs a rendered value, assert the value. networkidle is a proxy for “the page is ready”. Proxies fail when the page has analytics, polling, websockets, or a long-lived stream.

Pattern 4: Clicking an element that re-renders

The page replaces a button every 40 ms. The test clicks it.

await page.getByTestId('rerender-button').click({ timeout: 1000 });

Result: 18 of 20 runs passed. 2 failed with “element was detached from the DOM”.

Playwright waits for the element to be visible, stable, and able to receive events. It also retries when the element detaches. That is why most runs passed. But a 40 ms replacement cycle can still win the race.

The test-side fix is to click a stable control. The real fix is in the application: do not replace an interactive element while the user may be clicking it. A stable data-testid on a stable node is better than a perfect selector on a node that keeps changing.

In the lab, the fixed test clicks a stable button. That shows the test change. It does not pretend the application is fixed.

What the lab does not prove

This is a synthetic page. It does not have your network, your database, your feature flags, or your CI runner. A pattern that failed 14 of 20 times here may fail 1 of 100 times in your suite. The rate is not the point. The mechanism is.

The lab also used one machine and one browser. CI adds slower CPUs, shared runners, and different viewport sizes. Those change the timing, not the logic.

Do not copy the numbers into a report. Copy the method.

How to check your own suite

Start with one failing spec. Do not run the whole suite.

npx playwright test path/to/test.spec.ts --repeat-each=20 --workers=1

If it fails with one worker, the cause is likely timing, a locator, or the environment. If it passes with one worker and fails with several, look for shared state: a shared account, a fixed database row, a port, or a file.

Then run the same spec with the workers your CI uses. A test that fails only in parallel is a state problem, not a wait problem.

Turn on a trace for the first retry:

use: {
  trace: 'on-first-retry',
}

A trace shows the action, the DOM snapshot, the network, and the console at the moment of failure. It is faster than guessing.

When retries are the right answer

Retries are a short-term control. Use them to keep a release moving while you fix the cause. Set a limit, and track the flake rate. A test that passes on retry is still a flaky test.

Do not raise the global timeout to hide a race. A longer timeout makes the failure slower. It does not make the test more reliable.

The short answer

Four patterns, 80 runs. The fixed wait and the response race failed 70% of the time. The network wait failed when the poll started inside the quiet window. The re-render click failed less often, but it still failed.

The fixes are not clever. Wait for the visible state. Start the response wait before the click. Do not trust network idle on a polling page. Do not click an element that keeps being replaced.

Measure first. Fix the cause. Keep retries for the release, not for the diagnosis.

Frequently asked questions

What is a flaky test?

A flaky test passes and fails on the same code. The test result changes without a code change. That makes the result unreliable, even when the test is useful.

Do retries fix flaky tests?

No. Retries hide the failure and keep the build moving. They do not fix the timing, state, or environment problem that caused it. A test that passes on retry is still flaky.

Which pattern caused the most failures in the lab?

The fixed 250 ms wait and the response wait after the click both failed 14 of 20 runs. The re-rendering click failed 2 of 20. The network idle wait failed 3 of 20 when the poll started at a random time.

Can I use this lab on my own suite?

Yes. Run one failing spec with --repeat-each=20 and --workers=1. If it fails only with workers, look for shared state. If it fails with one worker, look for timing, locators, or the environment.
